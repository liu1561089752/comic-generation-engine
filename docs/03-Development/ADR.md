### ADR-001: 使用 PostgreSQL 而非 MongoDB

- **状态**: 已接受
- **日期**: 2026-06-27
- **决策者**: 架构师

#### 上下文

系统的核心数据（小说、角色、面板、图片元数据）具有复杂的关系结构，且需要 ACID 事务保证。在数据库选型时需要权衡关系型数据库和文档型数据库的优劣。

核心数据模型是一个严格的树形层级：`Project → Novel → Chapter → Scene → Panel → Shot/Bubble/Prompt → Image`。同时，AI 分析结果需要灵活的 JSON 存储能力。

#### 决策

使用 **PostgreSQL 15+** 作为主数据库。

#### 理由

1. **强关系性数据**：核心数据模型是严格的树形层级（Novel→Chapter→Scene→Panel 四级），天然适合关系型数据库的外键和 JOIN 查询
2. **事务保证**：批量操作（如整章生图）需要原子性保证，PostgreSQL 的 ACID 事务特性是关键需求
3. **JSONB 灵活性**：AI 分析结果（Scene 的人物列表、Prompt 的 10 层结构、图片的一致性报告）适合用 JSONB 字段存储，兼具文档数据库的灵活性和关系数据库的查询能力
4. **GIN 索引全文搜索**：PostgreSQL 的内置全文搜索（`to_tsvector` + GIN 索引）满足小说内容的搜索需求，无需额外引入 Elasticsearch
5. **SQLAlchemy 生态**：SQLAlchemy 2.0 对 PostgreSQL 的异步支持（asyncpg）最成熟，Alembic 迁移工具与 PostgreSQL 配合最佳
6. **成熟度和社区**：PostgreSQL 是开源数据库中最成熟、社区最活跃的选择，文档丰富，问题容易排查

#### 替代方案

- **MongoDB**：文档模型在树形数据上缺乏外键约束，容易产生数据不一致；不支持跨文档事务（V1 阶段无副本集）；关系查询（如"查某个角色的所有 Panel"）需要多次查询或聚合管道，性能不如 JOIN；全文搜索能力弱于 PostgreSQL
- **SQLite**：并发写入性能不足（WAL 模式也只能支持少量写并发），不满足生产过程多任务并发的需求；缺乏 JSONB 类型（用 TEXT 存储 JSON）
- **MySQL**：对 JSON 类型的支持不如 PostgreSQL 成熟；GIN 索引和全文搜索能力弱于 PostgreSQL；开发环境下不如 PostgreSQL 的 pgvector 等扩展生态

#### 后果

- **正面**：数据完整性得到保证；ORM 开发效率高；JSONB 字段兼顾灵活性和查询性能；内置全文搜索减少了外部依赖
- **负面**：需要对 JSONB 字段进行文档约束（否则可能存储脏数据）；ORM 的 N+1 查询问题需要留意（通过 selectinload/joinedload 解决）；PostgreSQL 部署比 SQLite 复杂

### ADR-002: Panel 作为最小操作单元

- **状态**: 已接受
- **日期**: 2026-06-27
- **决策者**: 架构师

#### 上下文

AI 漫画生产管线涉及多个粒度的数据单元（小说→章节→场景→画格→镜头→气泡），需要确定哪个粒度作为系统的最小操作单元，以支撑"可追溯"和"可迭代"的设计原则。

#### 决策

将 **Panel（画格）** 定义为系统的最小操作单元。一个 Panel 对应漫画中的一个独立画格（单幅画面），是生产管线的核心数据节点。

#### 理由

1. **业务完整性**：Panel 是小说文本到漫画画面的最小映射单元，一个 Panel 包含完整的上下文（原文片段、角色、动作、情绪）
2. **独立可迭代**：用户可以单独重新生成某个 Panel 的图片，而不影响其他 Panel；可以单独修改某个 Panel 的分镜、Prompt、气泡
3. **可追溯**：每个 Panel 持有 `scene_id → chapter_id → novel_id` 的完整上层链路，可以追溯到原文
4. **生图原子性**：AI 生图以 Panel 为粒度提交，单个 Panel 的 Prompt 生成和图片生成是独立的
5. **UI 一致性**：前端所有视图（分镜、版式、气泡、图片选择）都以 Panel 为中心展开，概念统一

#### 替代方案

- **Scene（场景）作为最小单元**：粒度太大，一个 Scene 包含多个画格，修改单个画格需要重新处理整个 Scene；无法支持"单独重画某个画格"的需求
- **Shot（镜头）作为最小单元**：粒度太小，Shot 是 Panel 的子级，多个 Shot 共享同一个构图和背景，单独操作 Shot 的语义不完整
- **Bubble（气泡）作为最小单元**：Bubble 是文本载体，不包含视觉信息，无法作为生图的独立单元

#### 后果

- **正面**：Panel 成为系统中最核心的表，管线的每个环节都围绕 Panel 展开；数据模型清晰；支持精细粒度的迭代操作
- **负面**：大量 Panel 数据（一部漫画可能上万 Panel）需要关注查询性能；Panel 之间的关联查询（如"查连续 Panel"）需要优化

### ADR-003: Prompt 最后生成（而非在剧情分析阶段）

- **状态**: 已接受
- **日期**: 2026-06-27
- **决策者**: 架构师

#### 上下文

在其他 AI 漫画工具中，Prompt 通常在剧情分析阶段或分镜阶段生成，随后直接调用生图。但在 AI Webtoon Factory 中，Prompt 被设计为管线的最后一步（第 8 步），在剧情分析、分镜规划、镜头规划、版式规划、气泡规划全部完成后才进行组装。

#### 决策

将 Prompt 生成放在管线**最后阶段**，在所有上游数据就绪后由专门的 Prompt 生成 Agent 聚合组装。

#### 理由

1. **数据完整性**：Prompt 需要聚合角色数据、场景数据、动作数据、镜头数据、版式数据、气泡数据、画风模板等，这些数据在管线前期和中期逐步就绪
2. **避免重复生成**：如果在剧情分析阶段就生成 Prompt，后续任何上游数据的修改（如更换角色服装、调整镜头）都导致 Prompt 的重新生成，造成浪费
3. **10 层结构化**：Prompt 的 10 层结构需要逐层填入具体数据，每层的数据来源不同（角色层来自人物 IP 中心，环境层来自世界观资产库，镜头层来自镜头规划 Agent），只有所有数据源就绪后才能完整组装
4. **模板化组装**：Prompt 生成本质是模板引擎 + 数据聚合的工作，不需要 LLM 参与，纯代码实现效率高、结果稳定

#### 替代方案

- **剧情分析阶段生成 Prompt**：缺乏角色 IP、场景资产等数据，生成的 Prompt 不够精确；后续修改上游数据导致 Prompt 失效
- **分镜阶段生成 Prompt**：缺乏镜头规划、版式规划数据，无法填充 camera 层和 composition 层
- **每个上游阶段逐步生成部分 Prompt**：需要维护部分 Prompt 的状态，复杂性高；层与层之间互相依赖，拆分困难

#### 后果

- **正面**：Prompt 质量高（数据完整）；修改上游数据不影响 Prompt 生成逻辑；Prompt 生成 Agent 实现简单（纯模板引擎）
- **负面**：用户需要完成所有上游操作后才能看到 Prompt 效果；如果只改 Prompt 内容（不改上游数据），需要提供手动编辑 Prompt 的能力

### ADR-004: 结构化 JSON 存储而非自然语言文本

- **状态**: 已接受
- **日期**: 2026-06-27
- **决策者**: 架构师

#### 上下文

AI 漫画工具的核心中间产物——Prompt、分镜描述、气泡文本、图片元数据等——需要决定存储为自然语言文本还是结构化 JSON。

#### 决策

所有中间产物均以**结构化 JSON** 格式存储，而非自然语言文本。

#### 理由

1. **机器可解析**：结构化数据可以被代码精确解析和操作，例如提取 Prompt 中的 character 层单独修改、从气泡数据中提取统计信息
2. **增量更新**：可以单独修改 JSON 中的某个字段（如只更新角色的服装描述）而不影响其他字段
3. **可追溯**：结构化数据可以记录每层的来源（如 character 层来自人物 IP 中心，camera 层来自镜头规划 Agent），支持完整的血统追溯
4. **版本对比**：对比两个版本的 Prompt 时，可以逐层 diff，而非逐行 diff 文本
5. **AI 输出精度**：要求 LLM 输出结构化 JSON（而非自由文本）可以约束输出格式，减少解析错误
6. **前端渲染**：前端可以按结构化数据渲染编辑器（如 10 层 Prompt 的独立编辑框），而非提供一个单行文本输入框

#### 替代方案

- **自然语言文本存储**：无法精准解析和操作；增量更新需要重新生成全文；版本对比粒度粗
- **Markdown 文本存储**：虽有一定的结构性，但无法程序化操作；解析和校验成本高

#### 后果

- **正面**：数据精确可控；支持细粒度操作；AI 输出质量更稳定；前端编辑体验好
- **负面**：需要维护 JSON Schema 约束，防止脏数据；JSONB 字段需要索引优化；后端需要编写序列化/反序列化逻辑

### ADR-005: 所有 AI Agent 输入输出均为结构化数据

- **状态**: 已接受
- **日期**: 2026-06-27
- **决策者**: 架构师

#### 上下文

系统包含 10 个 AI Agent 组成的处理管线，Agent 之间需要传递数据。需要统一约定 Agent 之间数据交换的格式。

#### 决策

**所有 AI Agent 的输入和输出均使用结构化 JSON 格式**，而非自然语言文本。Agent 之间的数据传递通过明确定义的 Pydantic Schema 约束。

#### 理由

1. **管线可编排**：结构化输入输出使得 Agent 可以像函数一样组合，前一个 Agent 的输出直接作为后一个 Agent 的输入
2. **类型安全**：Pydantic Schema 提供运行时类型校验，在开发阶段就能发现数据格式错误
3. **Mock 测试**：结构化数据可以方便地构造 Mock 数据，使得 Agent 可以独立测试，无需依赖上游 Agent
4. **结果可缓存**：相同的结构化输入一定能产生相同的结构化输出（确定性），支持结果缓存
5. **可观测性**：Agent 的输入输出可以完整记录到数据库，用于调试和审计

#### 替代方案

- **自然语言文本传递**：下游 Agent 需要自己解析文本，解析结果不可靠；无法类型校验；Mock 测试困难
- **共享数据库状态传递**：Agent 通过读写数据库来通信，耦合度高，管线编排困难

#### 后果

- **正面**：管线清晰、可测试、可观测；类型安全减少生产 bug；支持缓存和幂等性
- **负面**：Schema 定义和版本管理需要维护；Agent 实现需要额外的序列化/反序列化代码

### ADR-006: 10 层 Prompt 结构设计

- **状态**: 已接受
- **日期**: 2026-06-27
- **决策者**: 架构师

#### 上下文

生图模型的 Prompt 是影响图片质量的关键因素。需要设计一套结构化、可维护、可复用的 Prompt 体系，而非让用户/系统每次写一段不规范的文本。

#### 决策

采用 **10 层结构化 Prompt** 设计，每个 Panel 的 Prompt 由 10 个独立层组成，最终合并为完整的生图 Prompt。

#### 10 层定义

| 层级 | 名称 | 必填 | 数据来源 | 说明 |
|------|------|------|----------|------|
| 1 | **character** (角色) | 是 | 人物 IP 中心 | 角色外貌、服装、姿态描述 |
| 2 | **environment** (环境) | 是 | 世界观资产库 + Scene 数据 | 场景/背景描述 |
| 3 | **action** (动作) | 是 | 分镜规划 Agent + Panel 文本 | 角色动作/姿势描述 |
| 4 | **emotion** (情绪) | 是 | 剧情分析 Agent | 表情/情绪描述 |
| 5 | **camera** (镜头) | 是 | 镜头规划 Agent | 镜头类型、角度、运镜 |
| 6 | **lighting** (光照) | 是 | 镜头规划 Agent | 光照描述（类型、方向、色温） |
| 7 | **composition** (构图) | 是 | 镜头规划 Agent | 构图规则、画面比例 |
| 8 | **webtoon_style** (画风) | 是 | 风格模板库 | Webtoon 画风描述 |
| 9 | **bubble** (气泡) | 否 | 气泡规划 Agent | 气泡留白/文本布局说明 |
| 10 | **negative** (负向) | 否 | 系统预设 + 用户自定义 | 负向提示词 |

#### 理由

1. **关注点分离**：每层有明确的数据来源和负责的 Agent，修改某一层不影响其他层
2. **可复用模板**：Prompt 模板可以按层独立复用（如"温馨室内光照"模板可以复用于 lighting 层）
3. **精细化控制**：用户/系统可以单独调整某一层（如修改 character 层更换服装），而不影响其他 9 层
4. **A/B 测试**：可以固定其他 9 层，只测试某一层的不同写法对生图效果的影响
5. **版本管理友好**：版本 diff 可以精确到层级别

#### 替代方案

- **单段式 Prompt**：无法局部修改；版本管理粒度粗；A/B 测试无法隔离变量
- **5 层结构**：层数太少导致每层内容过多，失去精细控制能力
- **15+ 层结构**：过于细致，部分层数据来源重叠（如 action 和 motion 可以合并）

#### 后果

- **正面**：Prompt 质量可控、可归因、可迭代；模板复用率提高；A/B 测试能力
- **负面**：需要维护 10 层模板库；Prompt 生成 Agent 需要处理层之间的文本衔接（避免上下文跳跃）

### ADR-007: 图片存储使用文件系统/对象存储而非数据库 BLOB

- **状态**: 已接受
- **日期**: 2026-06-27
- **决策者**: 架构师

#### 上下文

系统需要存储大量 AI 生成的图片（单部漫画可能数千张），需要决定图片文件的存储方式。

#### 决策

图片存储在**文件系统（开发环境）/ MinIO 对象存储（生产环境）**，数据库中只存储文件路径/URL，不存储图片二进制数据。

#### 理由

1. **数据库性能**：BLOB 存储导致数据库体积迅速膨胀，影响备份、迁移和查询性能
2. **CDN 加速**：文件系统/对象存储可以方便地对接 CDN，加速图片加载
3. **独立扩展**：存储和数据库可以独立扩展，存储层可以按需扩容
4. **对象存储兼容**：MinIO 兼容 S3 API，未来可无缝迁移到 AWS S3、阿里云 OSS 等
5. **缩略图分离**：可以为每张图片生成多种尺寸的缩略图，数据库 URL 指向不同尺寸即可

#### 替代方案

- **数据库 BLOB**：数据库膨胀快，单个表破 GB 后备份和查询性能严重下降；无法利用 CDN
- **Base64 存储**：比 BLOB 更糟糕，体积增大 33%，无法直接访问

#### 后果

- **正面**：数据库保持轻量；图片可 CDN 加速；存储扩展灵活
- **负面**：需要维护文件系统和数据库之间的数据一致性（删除图片时需要同时删除文件和数据库记录）；需要额外的文件访问控制和权限检查

### ADR-008: 使用 Celery 而非内建线程池管理异步任务

- **状态**: 已接受
- **日期**: 2026-06-27
- **决策者**: 架构师

#### 上下文

AI 生图、AI 分析、导出等操作是耗时任务（数秒到数分钟），不能阻塞 API 响应。需要选择异步任务处理方案。

#### 决策

使用 **Celery** 作为异步任务队列框架，Redis 作为 Broker 和 Result Backend。

#### 理由

1. **分布式架构**：Celery 支持 Worker 分布式部署，可以为生图任务（GPU 密集型）和分析任务（CPU/IO 密集型）分配不同的 Worker 节点
2. **优先级队列**：支持多个队列（`ai_generation`、`ai_analysis`、`export`、`default`）和优先级控制，重要任务优先处理
3. **任务编排**：支持任务链（chain）、任务组（group）、任务依赖（chord），适合 AI 管线的编排需求
4. **重启恢复**：Worker 崩溃后未完成的任务可以重新调度（通过结果后端记录状态）
5. **进度追踪**：支持任务进度（`Task.update_state` 方法），前端可以实时显示进度条
6. **生态成熟**：Celery 是 Python 最成熟的分布式任务队列，文档丰富，问题容易排查

#### 替代方案

- **FastAPI 内建 BackgroundTasks**：仅适合快速轻量的后台任务（如发送邮件），不支持任务持久化、重试、优先级
- **Python asyncio 内建线程池**：单进程内运行，无法跨进程/跨机器扩展；进程崩溃后任务丢失；无失败重试机制
- **APScheduler**：更适合定时任务（cron 式调度），不适合长时间运行的队列任务
- **Redis Queue (RQ)**：比 Celery 轻量，但功能有限，不支持复杂的任务编排（chain/group/chord）

#### 后果

- **正面**：任务调度能力全面（优先级、编排、重试、进度追踪）；Worker 可独立扩展
- **负面**：引入 Redis 依赖增加了部署复杂度；Celery 的配置和学习成本较高；MVP 阶段可以先用同步模式简化

### ADR-009: 人物 IP 资产化（角色数据独立于 Prompt）

- **状态**: 已接受
- **日期**: 2026-06-27
- **决策者**: 架构师

#### 上下文

在其他 AI 漫画工具中，角色描述被"硬编码"在 Prompt 字符串中。一旦需要修改角色外观，需要修改所有涉及该角色的 Prompt。AI Webtoon Factory 需要更好的角色一致性管理方案。

#### 决策

将**角色（Character）设计为独立的资产实体**，拥有完整的属性定义（外貌、服装、性格、参考图等）。所有 Panel 的 Prompt 中的角色层通过变量引用角色 ID，而非直接写入角色描述文本。

#### 理由

1. **一致性保障**：所有角色数据集中维护，修改角色外观（如更换瞳色）后，涉及该角色的所有 Panel 自动更新
2. **版本管理**：角色本身可以有版本记录（如 V1 服装 → V2 服装），Panel 可以指定使用的角色版本
3. **精细控制**：角色可以拥有多套服装、多种表情、多个姿态，Panel 在生成 Prompt 时按需选择
4. **参考图系统**：Character 实体持有参考图 URL 列表（六视图 + 多角度），Prompt 生成时注入 ControlNet Reference-Only
5. **避免硬编码**：角色描述不再埋没在 Prompt 字符串中，而是作为独立数据源被复用

#### 替代方案

- **角色描述硬编码在 Prompt 中**：修改角色外观需要逐个修改所有 Prompt；无法复用角色数据；没有参考图关联
- **角色作为轻量标签**：只记录角色名和简单标签，缺乏足够精细的外观控制，LLM 需要从名称中"回忆"角色外观

#### 后果

- **正面**：角色一致性大幅提升；修改角色外观后所有 Panel 联动更新；支持多服装/多表情
- **负面**：需要实现"角色→Prompt"的变量替换机制；新增的角色字段需要同步更新 Prompt 模板中的对应变量

### ADR-010: 使用适配器模式解耦 AI 模型

- **状态**: 已接受
- **日期**: 2026-06-27
- **决策者**: 架构师

#### 上下文

系统依赖多个 AI 模型（LLM、生图模型、Embedding 模型、视觉检测模型），且需要支持模型的动态切换和扩展。直接依赖具体的 AI 库或 API 会导致耦合度过高。

#### 决策

使用**适配器模式（Adapter Pattern）** 抽象所有 AI 模型服务。每个模型类别定义一个抽象接口，所有具体实现（OpenAI、DeepSeek、SDAPI、Midjourney 等）实现该接口。

#### 理由

1. **可替换**：模型可以在不修改业务代码的情况下替换（如从 GPT-4 切换到 DeepSeek）
2. **可扩展**：新增模型只需要实现适配器接口，Agent 层完全感知不到变化
3. **可测试**：可以在测试中使用 MockAdapter 替代真实模型，无需网络连接
4. **兼容不同 API 格式**：不同模型的 API 格式差异很大（OpenAI 兼容 vs Midjourney 的轮询模式），适配器内部处理差异
5. **统一监控**：所有模型调用经过适配器层，可以统一记录日志、统计 Token 消耗

#### 替代方案

- **直接使用模型 SDK**：耦合度极高，切换模型需要修改大量业务代码；无法统一监控
- **函数抽象层**：粒度不够，每个模型的不同能力（chat、embed、stream）需要独立函数，难以统一管理

#### 后果

- **正面**：模型切换无感知；新增模型成本低；统一监控和日志
- **负面**：适配器接口需要平衡通用性和灵活性（通用接口无法覆盖所有模型的特殊能力，需要用 kwargs 透传）; 对于不同模型的特性参数（如 MJ 的 --stylize），需要在适配器内部做参数映射

### ADR-011: 漫画编辑器使用 Konva.js 而非纯 DOM

- **状态**: 已接受
- **日期**: 2026-06-27
- **决策者**: 前端架构师

#### 上下文

漫画编辑器需要在浏览器中实现复杂的 Canvas 编辑功能，包括图层管理、图片拖拽缩放、气泡编辑、特效叠加等。需要选择适合的渲染方案。

#### 决策

使用 **Konva.js（通过 react-konva）** 实现漫画编辑器，而非纯 DOM 操作。

#### 理由

1. **Canvas 性能**：漫画页面包含高分辨率图片和多个图层，DOM 树渲染大量节点会导致页面卡顿，Canvas 渲染更高效
2. **图层管理**：Konva.js 原生支持图层（Layer）、组（Group）、变换（Transformer），适合漫画编辑中的图层操作
3. **拖拽缩放**：Konva.js 内置拖拽（Draggable）和缩放（Transformer）功能，减少自定义实现
4. **事件处理**：支持事件委托和命中检测（Hit Detection），精确处理画格、气泡、特效的点击和选择
5. **导出能力**：Konva.js 支持 `toDataURL()` 和 `toBlob()` 方法，可以直接导出 Canvas 内容为图片
6. **React 集成**：react-konva 提供了声明式的组件 API，与 React 数据流无缝集成

#### 替代方案

- **纯 DOM + CSS**：大量高分辨率图片导致 DOM 节点过多，性能差；图层叠加需要复杂的 z-index 管理；拖拽/缩放需要从零实现
- **原生 Canvas API**：需要从零实现图层管理、事件处理、拖拽逻辑，开发成本高
- **Fabric.js**：功能类似 Konva.js，但 TypeScript 类型定义不如 Konva.js 完善，React 集成不如 react-konva 成熟

#### 后果

- **正面**：编辑器性能好；开发效率高（内置图层、拖拽、变换功能）；导出能力强
- **负面**：Canvas 内的文本渲染不如 DOM 精细（字体渲染差异）；SEO 不友好（但编辑器不需要 SEO）；增加包体积（Konva.js ~500KB）

### ADR-012: 前端状态管理使用 Zustand 而非 Redux

- **状态**: 已接受
- **日期**: 2026-06-27
- **决策者**: 前端架构师

#### 上下文

前端需要管理复杂的应用状态，包括项目数据、路由状态、AI 任务状态、编辑器状态等。需要选择状态管理方案。

#### 决策

使用 **Zustand** 作为前端状态管理库，而非 Redux。

#### 理由

1. **轻量无依赖**：Zustand 核心不到 1KB（minified + gzipped），无 Provider 嵌套、无 Action/Reducer 模板代码
2. **TypeScript 友好**：Zustand 的类型推导自然，不需要像 Redux 那样定义大量的 Action Type 和 Selector 类型
3. **按需拆分 Store**：可以为每个模块创建独立的 Store（`novelStore`、`panelStore`、`taskStore`），避免 Redux 的单一 Store 臃肿
4. **中间件支持**：支持 `persist`（持久化到 localStorage/IndexedDB）、`devtools`（Redux DevTools）、`subscribe`（监听变化）等中间件
5. **无 Provider 嵌套**：Zustand 的 Store 是独立的事件总线，不需要在 React 组件树中添加 Provider，减少嵌套层级
6. **与 React 18 兼容**：Zustand 4.x 使用了 React 18 的 `useSyncExternalStore`，避免 tearing 问题

#### 替代方案

- **Redux Toolkit (RTK)**：功能强大，但样板代码多（Slice/Action/Reducer/Selector），开发效率低于 Zustand；需要 Provider 包裹；不适合中等复杂度的应用
- **React Context + useReducer**：Context 的 Value 变化会导致所有 Consumer 重新渲染，性能不如 Zustand 的细粒度订阅；不适合复杂状态管理
- **MobX**：响应式编程模型，但可变数据（Mutable）在 React 中容易引起问题；TypeScript 类型推导不如 Zustand 自然

#### 后果

- **正面**：开发效率高，代码简洁；TypeScript 类型完整；性能好（细粒度订阅）
- **负面**：Zustand 没有官方推荐的 Store 组织方式，需要团队约定 Store 结构；中间件生态不如 Redux 丰富

### ADR-013: MVP 阶段使用 SQLite，V2 强制 PostgreSQL

- **状态**: 已接受
- **日期**: 2026-06-27
- **决策者**: 架构师

#### 上下文

开发环境和部署环境的数据库选型需要平衡开发效率和功能完整性。

#### 决策

MVP 阶段**默认使用 SQLite** 作为开发/单机部署数据库，V2 阶段起**强制使用 PostgreSQL**。

#### 理由

1. **零配置部署**：SQLite 不需要安装、不需要配置、不需要守护进程，降低开发者和用户的入门门槛
2. **开发效率**：开发者无需在本地安装 PostgreSQL，clone 仓库后即可运行
3. **单用户适配**：MVP 阶段是单用户模式，SQLite 的并发能力足够
4. **SQLAlchemy 抽象**：ORM 层使用 SQLAlchemy，切换数据库只需要修改连接字符串，代码无需变更
5. **V2 升级路径**：V2 阶段需要并发写入（多任务）、全文搜索、JSONB 等特性，届时强制 PostgreSQL 并提供迁移工具

#### 替代方案

- **全程 PostgreSQL**：部署复杂度高，增加开发者入门成本
- **全程 SQLite**：无法支持 V2 阶段的多任务并发和全文搜索需求

#### 后果

- **正面**：MVP 开发效率高，部署门槛低；SQLAlchemy 保证迁移路径清晰
- **负面**：SQLite 不支持 JSONB 和 GIN 索引，部分功能在 MVP 阶段需要降级实现（如用 TEXT 存储 JSON）；V2 升级时需要数据迁移工具

### ADR-014: 前端路由以功能模块划分，而非页面层级

- **状态**: 已接受
- **日期**: 2026-06-27
- **决策者**: 前端架构师

#### 上下文

系统包含 15+ 个功能页面（工作台、小说管理、人物 IP、分镜中心、版式中心等），前端的路由设计需要确定组织方式。

#### 决策

前端路由**以功能模块为一级路径**，而非按页面层级深度嵌套。

#### 路由结构

```
/dashboard                  → 工作台
/projects/{id}              → 项目详情页
/projects/{id}/novels       → 小说管理
/projects/{id}/characters   → 人物 IP 中心
/projects/{id}/worlds       → 世界观资产库
/projects/{id}/breakdown    → 剧情拆解中心
/projects/{id}/storyboard   → 分镜中心
/projects/{id}/layout       → 版式中心
/projects/{id}/text         → 漫画文本中心
/projects/{id}/prompts      → Prompt 中心
/projects/{id}/generation   → AI 生图中心
/projects/{id}/quality      → 质量控制中心
/projects/{id}/editor       → 漫画编辑器
/projects/{id}/export       → 导出中心
/projects/{id}/resources    → 资源中心
/settings/models            → AI 模型中心
/settings/plugins           → 插件中心
/settings/system            → 系统管理
/help                       → 帮助中心
```

#### 理由

1. **扁平化导航**：所有功能模块在同一层级，用户可以通过侧边栏快速切换，操作路径短
2. **项目上下文传递**：以 `project_id` 为上下文，所有项目内页面共享同一个项目上下文，无需深层参数传递
3. **代码分割清晰**：每个模块可以独立做 React.lazy 代码分割，按需加载
4. **URL 可读性强**：路由路径直接对应功能模块名，用户和开发者都能快速理解
5. **扩展性强**：新增功能模块只需添加一级路由，不影响现有路由结构

#### 替代方案

- **按页面层级深度嵌套**：如 `/projects/{id}/chapters/{ch_id}/scenes/{sc_id}/panels/{panel_id}`，URL 过长；导航层级深，操作路径长
- **按操作类型划分**：如 `/create/novel`、`/edit/panel/123`，缺乏一致性，难以维护

#### 后果

- **正面**：导航效率高；代码分割粒度好；URL 结构清晰
- **负面**：需要处理 `project_id` 的全局状态传递；某些子页面（如 Panel 详情）需要额外的 query 参数定位

### ADR-015: 后端使用 Repository 模式分离数据访问

- **状态**: 已接受
- **日期**: 2026-06-27
- **决策者**: 架构师

#### 上下文

后端包含多层次代码（路由层、服务层、AI Agent 层、数据访问层），需要组织分层以避免循环依赖和职责混乱。

#### 决策

采用 **Repository 模式** 将数据访问逻辑从服务层中分离，每个核心实体拥有独立的 Repository 类。

#### 理由

1. **关注点分离**：Service 层关注业务逻辑和管线编排，Repository 层关注 SQL 查询和数据访问，职责清晰
2. **可测试性**：Repository 可以轻松 Mock，Service 层的单元测试不需要真实的数据库连接
3. **查询复用**：复杂的查询（如"查某角色在某一章的所有 Panel"）封装在 Repository 中，多处复用
4. **事务管理**：事务边界在 Service 层控制，Repository 的方法默认不提交事务，由 Service 层统一管理
5. **ORM 隔离**：如果将来需要替换 ORM（如从 SQLAlchemy 换到其他 ORM），只需要替换 Repository 层

#### 替代方案

- **Service 层直接使用 ORM**：SQL 查询散布在业务逻辑中，难以复用和维护；测试需要真实数据库
- **Active Record 模式**：SQLAlchemy 本身就是 Active Record 风格，直接使用会导致 Service 层与 ORM 耦合过紧

#### 后果

- **正面**：代码结构清晰，测试性好；查询逻辑集中管理；ORM 变更影响范围小
- **负面**：引入额外的抽象层，简单 CRUD 操作需要写 3 层代码（Schema → Service → Repository）；项目初期需要更多的脚手架代码
