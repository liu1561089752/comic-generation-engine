## 风险等级定义

| 等级 | 概率 | 影响 |
|------|------|------|
| ★★★★★ | >80% / 极可能发生 | 项目失败/完全不可用 |
| ★★★★☆ | 60-80% / 很可能 | 核心功能不可用/严重延期 |
| ★★★☆☆ | 40-60% / 可能 | 部分功能受损/中度延期 |
| ★★☆☆☆ | 20-40% / 不太可能 | 次要功能受损/轻微延期 |

## 风险列表

### R001: AI 角色一致性无法达到商业标准

- **风险等级**: ★★★★★
- **概率**: 高（75%）
- **影响**: 高（角色在不同画格中变化，漫画无法发布）
- **风险分类**: AI 技术风险

#### 表现

同一角色在连续画格中出现发色/发型/瞳色/服装/面部特征的不一致。这是当前 AI 生图技术（即使是 Stable Diffusion XL / Midjourney V6）的普遍问题。对于需要数 10 个角色、数百画格的商业 Webtoon，不一致率可能在 30-60%。

#### 根本原因

1. 生图模型每次生成都是从噪声开始随机采样，即使相同 Prompt 也可能产生不同结果
2. 当前 ControlNet Reference-Only 技术对角色一致性的控制能力有限
3. 无法保证同一角色在不同构图（正面/侧面/背面）、不同光照、不同情绪下保持一致
4. 长篇小说中角色经历时间线变化（成长、换装、受伤等），更增加了一致性的难度

#### 缓解措施

1. **参考图系统（六视图 + 多角度）**
   - 每个角色建立完整的六视图参考图库（正面/背面/左侧/右侧/45度/特写表情）
   - Prompt 生成时自动注入参考图 URL，配合 ControlNet Reference-Only 使用
   - 执行计划：Sprint 3 实现参考图管理功能，Sprint 5 集成到生图管线

2. **ControlNet / Reference-Only 技术接入**
   - SDAPI 适配器支持 ControlNet 参数透传（`controlnet_units` 参数）
   - 优先级最高的 ControlNet 单元配置为 Reference-Only 模式
   - 执行计划：Sprint 5 集成，V2 阶段优化参数配置

3. **多候选图（A/B/C/D）+ 人工选择**
   - 每个 Panel 默认生成 4 张候选图（可配置 2-8 张）
   - 前端提供画廊对比视图，支持横向/纵向比较
   - 人工选择后将 `seed` 和 `prompt` 版本锁定，支持后续以相同参数重新生成
   - 执行计划：Sprint 5 核心功能，Sprint 6 完善对比 UI

4. **AI 一致性自动检测报警**
   - 一致性检查 Agent（Agent ⑨）对生成图片做逐维度检测
   - 检测维度：发色、发型、瞳色、肤色、服装类型、面部结构
   - 低于阈值（< 80%）的图片自动标记为"待复审"，进入人工审核通道
   - 执行计划：V2 阶段（Sprint 9-10）

5. **同批次生图锁定 seed**
   - 同一 Scene 下连续 Panel 的生图使用连续的 seed（如 seed=100, 101, 102...）
   - 确保同一场景内的光照、色调、角色摆位保持连贯
   - 执行计划：Sprint 5

#### 应急预案

- **短期**（MVP 阶段不可用时）：对关键角色使用 IP-Adapter 或 LoRA 微调，训练专属模型
- **中期**：建立角色专属 LoRA 模型库，每个角色在项目初始化时训练专属 LoRA
- **长期**：调研更先进的一致性控制技术（如 ID-Animator、InstantID 等）

AI 工程师

### R002: LLM Prompt 漂移

- **风险等级**: ★★★★★
- **概率**: 高（80%）
- **影响**: 中（AI 分析质量不稳定，输出格式不一致）
- **风险分类**: AI 技术风险

#### 表现

同一 Prompt 在不同时间点调用 LLM 时返回不同的结果结构，导致下游解析失败。LLM 的版本更新（如 GPT-4 → GPT-4-turbo → GPT-4o）会引入行为变化，模型供应商在未经通知的情况下更新模型行为。

#### 根本原因

1. LLM 供应商频繁更新模型（OpenAI 每月多次微调更新）
2. 模型对格式描述的敏感度不同（"Return JSON"在 GPT-4 上稳定，但在某些模型上不稳定）
3. 模型输出存在随机性（即使 temperature=0 也无法保证 100% 稳定）
4. 多轮对话中上下文窗口的边缘区域质量下降

#### 缓解措施

1. **输入输出 JSON Schema 严格校验**
   - 每个 Agent 的输出使用 Pydantic Schema 进行运行时校验
   - 解析失败时自动重试（最多 3 次），每次重试将错误信息注入 Prompt 要求修正
   - 执行计划：Sprint 4（Agent 层开发时同步实现）

2. **每次 LLM 调用记录完整日志**
   - 所有 Agent 的输入输出完整记录到 `agent_call_log` 表
   - 包含：时间戳、模型版本、输入 messages、原始输出、解析结果
   - 执行计划：Sprint 4

3. **定期回归测试**
   - 维护测试用例集（每类 Agent 5-10 个典型场景）
   - 每周全量回归测试，输出格式正确性评分
   - 格式正确率低于 95% 时触发告警
   - 执行计划：V2 阶段建立自动化回归测试

4. **固定 LLM 版本号**
   - 配置中指定具体模型版本号（如 `gpt-4o-2024-08-06`），而非 `gpt-4o`
   - 版本更新走灰度发布，先在小范围测试再全量切换
   - 执行计划：Sprint 4

#### 应急预案

- 发现格式不稳定时，立即切换回上一版本模型
- 在 Agent 实现中增加"raw output fallback"模式：当 JSON 解析失败时，使用正则/规则从原始输出中提取关键信息
- 紧急情况下切换到备选 LLM（如从 GPT-4o 切到 DeepSeek）

#### 责任人

AI 工程师

#### 状态

活跃

### R003: 生图模型 API 更新/下线

- **风险等级**: ★★★★★
- **概率**: 中（50%）
- **影响**: 高（核心生图功能不可用）
- **风险分类**: 外部依赖风险

#### 表现

正在使用的生图模型 API 发生不兼容更新、定价变更或服务下线，直接导致 AI 生图模块不可用。Stable Diffusion WebUI 社区版也可能因依赖冲突导致无法正常启动。

#### 缓解措施

1. **适配器模式支持多模型切换**
   - ImageGenAdapter 接口隔离，Agent 层不依赖具体模型
   - 新增模型只需实现适配器接口，无需修改 Agent 代码
   - 执行计划：Sprint 5（适配器模式）

2. **至少维护 2 个可用生图后端**
   - 主后端：SDXL（通过 SDAPIAdapter / ComfyUIAdapter）
   - 备后端：Midjourney（通过 MJ-Proxy）
   - 第三备选：豆包/通义万相/OpenAI DALL-E（根据 API 兼容性）
   - 执行计划：MVP 阶段 1 个后端，V2 阶段 2 个，V3 阶段 3+

3. **本地部署备选模型**
   - 将 SDXL 模型预装在 Docker 镜像中
   - 无法连接外部 API 时自动切换到本地 SDXL 部署
   - 执行计划：V2 阶段

4. **熔断机制**
   - 连续失败超过阈值（5 次）时触发熔断，自动切换到备用后端
   - 熔断恢复后定期发探测请求恢复主后端
   - 执行计划：V2 阶段

#### 应急预案

- 主后端不可用时：自动/手动切换到备用后端（切换时间 < 30 秒）
- 所有后端不可用时：系统降级为"仅编辑模式"，用户可离线编辑已有数据
- 关键 API 下线时：提供迁移脚本和数据导出工具

#### 责任人

架构师

#### 状态

活跃

### R004: API Token 成本失控

- **风险等级**: ★★★★☆
- **概率**: 中（60%）
- **影响**: 中（项目预算超支，影响持续运行）
- **风险分类**: 运营风险

#### 表现

生成一部漫画的 API 调用成本超出预算。一部 200 话的 Webtoon 预估可能需要数万次 LLM 调用和数千次生图调用，月成本可能达到数千美元。

#### 成本估算

| 任务类型 | 每话预估 | 单价 | 200 话成本 |
|----------|----------|------|-----------|
| LLM 分析（GPT-4o） | 5-10 次调用，~4000 tokens/次 | $0.01/次 | $10-20 |
| 生图（SDXL） | 60-120 张（含候选图） | $0.02/张 | $240-480 |
| 一致性检测 | 60-120 次 | $0.01/次 | $120-240 |
| **合计** | | | **$370-740/部** |

#### 缓解措施

1. **Token 消耗统计和预警**
   - 每次模型调用记录详细消耗，支持按项目/按时间段统计
   - 日消耗超过预算阈值时触发告警（邮件/WebSocket 通知）
   - 月消耗达到预算 80%/100% 时发送阶梯式告警
   - 执行计划：Sprint 5

2. **批量操作合并 Prompt 减少调用次数**
   - LLM 分析任务合并批量处理（一次调用分析 5-10 个 Panel）
   - 压缩输入 Prompt 中的上下文信息（只保留关键数据）
   - 执行计划：Sprint 4

3. **支持低成本模型**
   - 分析任务可配置使用不同性价比的模型：
     - 核心分析（剧情分析、语义切句）→ GPT-4o（高质量）
     - 辅助分析（分镜规划、镜头规划）→ GPT-4o-mini / DeepSeek（低成本）
     - 简单格式化任务 → 规则引擎替代 LLM
   - 执行计划：Sprint 4（模型选择机制）

4. **生图分辨率分级**
   - 分镜预览阶段：低分辨率（540×720），快速出图，成本降低 60%
   - 定稿阶段：全分辨率（1080×1440），最终导出
   - 执行计划：Sprint 5

5. **缓存相同 Prompt 的生图结果**
   - 对 `prompt_hash + model + seed + 参数` 做缓存
   - 相同 Panel 的重新生成直接返回缓存结果
   - 执行计划：V2 阶段

6. **本地部署开源模型降本**
   - 本地部署 DeepSeek（替代 GPT-4 的分析任务）
   - 本地部署 SDXL（降低生图 API 调用成本）
   - 执行计划：V2 阶段

#### 应急预案

- 紧急情况下暂停所有 AI 生成任务，仅保留手动编辑功能
- 将模型配置从高性能模型切到低成本模型，优先保证功能可用
- 增加候选图之间的复用（如同一角色的不同 Panel 共享背景图）

#### 责任人

产品经理

#### 状态

活跃

### R005: 图片存储空间爆炸

- **风险等级**: ★★★★☆
- **概率**: 中（60%）
- **影响**: 中（存储成本增加，系统运行受影响）
- **风险分类**: 运维风险

#### 表现

每一张生成图（1080×1440 PNG）约 1-3MB，加上候选图、缩略图、版本历史，单个项目的存储占用可能达到数 GB 到数十 GB。多项目并行时存储空间迅速耗尽。

#### 缓解措施

1. **自动清理临时图**
   - 未被选为"最终图"的候选图保留 30 天后自动清理
   - "已拒绝"的图片保留 7 天后清理
   - 执行计划：Sprint 6

2. **缩略图生成**
   - 每张原图自动生成 3 种尺寸的缩略图：
     - 小图（thumbnail）：300px 宽，WebP，质量 80%，用于列表展示
     - 中图（preview）：1080px 宽，WebP，质量 90%，用于编辑预览
     - 原图（original）：原始分辨率，PNG，用于最终导出
   - 执行计划：Sprint 6

3. **压缩策略**
   - 预览图默认使用 WebP 格式（比 PNG 小 60-80%）
   - 最终导出时使用 PNG 无损格式
   - 执行计划：Sprint 6

4. **归档策略**
   - 项目归档（status=archived）后，保留数据库记录，可选清理图片文件
   - 归档超过 180 天的项目，图片文件自动移至冷存储（低成本归档存储）
   - 执行计划：V2 阶段

#### 应急预案

- 存储空间低于 20% 时触发告警
- 自动切换为"低存储模式"：缩略图质量降低到 60%，候选图数量减半
- 紧急扩容：增加存储空间配额或切换对象存储

#### 责任人

后端工程师

#### 状态

活跃

### R006: 长篇小说处理性能瓶颈

- **风险等级**: ★★★☆☆
- **概率**: 中（40%）
- **影响**: 中（处理时间过长，用户体验差）
- **风险分类**: 性能风险

#### 表现

处理 50 万字以上的长篇网络小说时，单次 AI 分析可能耗时 30 分钟以上，前端长时间无反馈。LLM 上下文窗口限制（128K tokens ≈ 8-10 万中文字符）导致无法一次性分析完整本小说。

#### 缓解措施

1. **分章节处理**
   - 以章节为基本处理单元，每章独立分析
   - 支持按章节/按批次提交分析任务，而非整本小说
   - 执行计划：Sprint 4

2. **异步管线**
   - AI 分析任务通过 Celery 异步执行，不阻塞 API 响应
   - 前端通过 WebSocket 接收任务进度更新
   - 支持"提交分析后离开，完成后通知"的工作模式
   - 执行计划：Sprint 4（API 层），Sprint 7-8（Celery 集成）

3. **进度条和预估时间**
   - 前端实时显示处理进度（已完成/总计）
   - 基于已完成部分的平均耗时估算剩余时间
   - 执行计划：Sprint 4

4. **增量处理**
   - 如果修改了某章内容，只需重新分析该章，不影响其他已完成的章节
   - 执行计划：V2 阶段

#### 应急预案

- 处理时间过长（超过 1 小时）时自动终止，提示用户分批次处理
- 提供"跳过 AI 分析，手动创建 Scene/Panel"的备选路径

#### 责任人

后端工程师

#### 状态

活跃

### R007: 数据库性能随着项目数增长下降

- **风险等级**: ★★★☆☆
- **概率**: 中（40%）
- **影响**: 中（页面加载变慢，操作响应延迟）
- **风险分类**: 性能风险

#### 表现

随着项目数量增加和单项目的 Panel 数增长（1000+ Panel），数据库查询速度下降。Panel 列表翻页、按状态筛选、跨表的关联查询（Panel + Image + Prompt）变得缓慢。

#### 缓解措施

1. **索引策略**
   - 所有外键和筛选字段建立 BTREE 索引
   - 高频复合查询建立复合索引（如 `(scene_id, status)`、`(panel_id, is_selected)`）
   - 稀疏字段使用部分索引（如 `WHERE is_selected = TRUE`）
   - 执行计划：Sprint 1（初始索引），持续优化

2. **分页查询**
   - 所有列表接口强制分页（page_size 最大 100）
   - 使用 Keyset Pagination（基于 `id` 或连续递增字段）替代 Offset Pagination
   - 执行计划：Sprint 1

3. **数据归档**
   - 已归档项目的查询频率低，可归档到单独的表或分区
   - 历史数据定期迁移到归档表，减少主表体积
   - 执行计划：V2 阶段

4. **读写分离（V3）**
   - 配置 PostgreSQL 主从复制
   - 写操作走主库，读操作走从库
   - 执行计划：V3 阶段

5. **Redis 缓存**
   - 热门数据（项目统计、角色列表、Panel 状态）缓存到 Redis
   - 缓存失效策略：写入时主动失效，TTL 最大 5 分钟
   - 执行计划：Sprint 5（基础缓存），V2 阶段（全面缓存）

#### 应急预案

- 数据库查询超过 500ms 时自动记录慢查询日志
- 每周审查慢查询日志，针对性优化
- 紧急情况下对高频查询使用 Redis 全量缓存

#### 责任人

后端工程师

#### 状态

活跃

### R008: AI 分析结果质量不稳定

- **风险等级**: ★★★☆☆
- **概率**: 中（50%）
- **影响**: 中（用户需要手动修正分析结果）
- **风险分类**: AI 技术风险

#### 表现

AI 对剧情结构的分析结果不够精确，如 Scene 边界识别错误、人物提取遗漏、场景情绪判断不准。用户需要大量手动修正，降低了"AI 辅助"的价值。

#### 典型错误

1. **Scene 边界过多/过少**：将同一场景误拆分为多个 Scene，或将不同场景合并为一个
2. **人物识别错误**：漏识别场景中的角色，或张冠李戴
3. **情绪判断不准确**：激烈对峙场景被判断为"平静"
4. **语义切句不合理**：切分出的 Panel 信息量不均匀（有的太复杂，有的太简单）

#### 缓解措施

1. **Prompt 优化**
   - 为每个 Agent 设计专门的 System Prompt，包含详细的任务说明和输出格式约束
   - 加入 few-shot 示例（3-5 个典型场景的输入输出示例）
   - 使用 Chain-of-Thought（CoT）提示引导 LLM 逐步推理
   - 执行计划：Sprint 4（持续优化）

2. **few-shot 示例**
   - 每个 Agent 的 Prompt 中嵌入高质量的手工标注示例
   - 示例覆盖主流题材（现代、古代、玄幻、校园等）
   - 执行计划：Sprint 4

3. **人工审核环节**
   - 每个 Agent 的输出结果都有配套的人工审核界面
   - 用户可以接受、修改或打回重新生成
   - 修改后的结果作为"反馈数据"记录，用于后续优化
   - 执行计划：Sprint 4（Scene 审核），Sprint 5（Panel 审核）

4. **质量评分**
   - 质量评分 Agent（Agent ⑩）对分析结果进行自评

- 严重情况下，允许用户跳过特定 Agent 的处理，直接从上游数据手动编辑

### R009: 第三方依赖变更风险

- **风险等级**: ★★☆☆☆
- **概率**: 低（30%）
- **影响**: 中（构建失败或功能异常）
- **风险分类**: 运维风险

#### 表现

第三方库的版本更新引入破坏性变更、弃用 API、或安全漏洞。Python 生态的依赖冲突（如 torch + transformers + diffusers 的版本不兼容）导致环境无法启动。

#### 缓解措施

1. **依赖版本锁定**
   - 后端使用 `requirements.txt` + `pip freeze` 锁定所有依赖的精确版本
   - 前端使用 `package-lock.json` / `yarn.lock` 锁定依赖
   - Docker 构建时使用固定基础镜像版本（如 `python:3.11-slim-bookworm`）
   - 执行计划：Sprint 1

2. **定期更新审计**
   - 每月执行一次 `pip-audit` 和 `npm audit` 检查安全漏洞
   - 每季度执行一次依赖版本评估，升级次要版本
   - 执行计划：Sprint 1 起持续执行

3. **Docker 镜像缓存**
   - 使用 Docker layer caching 加速构建
   - 依赖层缓存，只在 `requirements.txt` 变更时重新构建
   - 执行计划：Sprint 1

4. **CI 流水线依赖检查**
   - PR 合并前自动检查依赖变更
   - 新依赖需经过安全审查
   - 执行计划：Sprint 1

#### 应急预案

- 关键依赖出现安全漏洞时，24 小时内升级到修复版本
- 依赖不可修复时（如库已停维护），寻找替代方案并制定迁移计划

### R010: 用户误操作数据丢失

- **风险等级**: ★★☆☆☆
- **概率**: 中（40%）
- **影响**: 高（用户失去大量工作成果）
- **风险分类**: 用户体验风险

#### 表现

用户误删除项目/章节/角色、编辑未保存、覆盖了之前的版本等操作导致数据丢失。对于耗时数天到数周的漫画制作项目，数据丢失的打击可能是毁灭性的。

#### 缓解措施

1. **软删除（7 天回收站）**
   - 项目、章节、角色等核心实体使用软删除机制
   - 标记 `deleted_at` 时间戳，7 天内可从回收站恢复
   - 7 天后物理删除（或在归档表中保留）
   - 执行计划：Sprint 2（项目级），V2 阶段（全面）

2. **版本历史**
   - Prompt、Image 等可编辑实体支持版本管理
   - 用户可以回退到任意历史版本
   - 版本保留上限：100 版本/Panel（超出后自动淘汰最旧版本）
   - 执行计划：Sprint 5

3. **自动保存**
   - 前端编辑器每 30 秒自动保存当前编辑内容
   - 切换页面/关闭标签页前提示未保存内容
   - 使用 `beforeunload` 事件拦截意外关闭
   - 执行计划：Sprint 2（基础自动保存），Sprint 6（编辑器自动保存）

4. **操作确认弹窗**
   - 所有删除操作显示确认对话框
   - 批量操作（整章删除、批量重新生成）显示操作预览和规模提示
   - 执行计划：Sprint 2

5. **定期备份**
   - 系统每日自动备份数据库
   - 备份保留 30 天
   - 支持手动触发备份和按需恢复
   - 执行计划：V2 阶段

#### 应急预案

- 用户发现误操作后，通过回收站恢复（7 天内）
- 回收站已清理的，从每日备份中恢复（30 天内）
- 超过 30 天的，提供"归档数据提取"服务（需人工介入）

### R011: 前端漫画编辑器性能问题

- **风险等级**: ★★★☆☆
- **概率**: 中（50%）
- **影响**: 中（编辑体验卡顿，用户流失）
- **风险分类**: 性能风险

#### 表现

漫画编辑器中同时加载多个高分辨率 Panel 图片（每个 1080×1440，约 1-3MB），浏览和编辑时出现卡顿、内存占用过高、操作响应延迟等问题。特别是长图预览模式，几十个 Panel 连续加载时浏览器可能崩溃。

#### 根本原因

1. 多个高分辨率图片同时渲染消耗大量 GPU 内存
2. Konva.js Canvas 的 hit detection 在大场景下性能下降
3. 气泡拖拽、图层变换等交互操作需要实时重绘
4. 长图预览时滚动和缩放的计算开销大

#### 缓解措施

1. **图片分级加载**
   - 缩略图模式（编辑预览）：使用 300px 宽度的缩略图
   - 编辑模式（单个 Panel 编辑）：使用 1080px 宽的预览图
   - 导出模式：使用原始分辨率图片
   - 执行计划：Sprint 6

2. **虚拟滚动**
   - 长图预览时使用虚拟滚动，只渲染可视区域内的 Panel
   - 非可视区域使用低分辨率占位图
   - 执行计划：V2 阶段（Sprint 11）

3. **Web Worker 处理图片解码**
   - 图片解码、Base64 转换在 Web Worker 中执行
   - 主线程只负责渲染，不阻塞 UI 操作
   - 执行计划：V2 阶段

4. **Canvas 渲染优化**
   - 限制最大帧率（30fps 足够编辑器交互）
   - 使用 Konva.js 的 batch draw 减少重绘次数
   - 不在视口中的 Layer 跳过渲染
   - 执行计划：Sprint 6

5. **内存管理**
   - 离开编辑器页面时手动释放 Canvas 资源
   - 缓存 LRU 策略，淘汰最久未使用的图片
   - 执行计划：Sprint 6

#### 应急预案

- 检测到内存不足时，自动降低显示的图片质量等级
- 编辑器内提示用户"性能不足，建议分章节编辑"
- 严重卡顿时提供"简化模式"：仅显示 Panel 边框和占位符

#### 责任人

前端工程师

#### 状态

活跃

### R012: 多用户场景（V3）权限控制缺陷

- **风险等级**: ★★☆☆☆
- **概率**: 低（20%）
- **影响**: 高（数据泄露或越权操作）
- **风险分类**: 安全风险

#### 表现

V3 阶段引入多用户系统后，权限控制系统可能存在漏洞，导致用户能够访问/修改不属于自己的项目数据。

#### 缓解措施

1. **数据隔离设计**
   - 所有核心数据表（project, novel, character 等）都持有一个 `user_id` 或 `project_id` 字段
   - 所有 API 查询自动追加用户/项目权限过滤条件
   - 执行计划：V3 阶段（Sprint 16-18）

2. **权限中间件**
   - 开发通用的权限检查中间件，在路由层统一拦截
   - 权限检查逻辑与服务层分离，通过装饰器或依赖注入实现
   - 执行计划：V3 阶段

3. **安全审计**
   - 每次 API release 前进行权限安全审查
   - 使用自动化测试覆盖权限边界场景（越权读、越权写、越权删）
   - 执行计划：V3 阶段

#### 应急预案

- 发现权限漏洞后，立即修复并通知受影响的用户
- 实现完整的操作审计日志，支持事后追溯

### R014: AI 模型供应商服务不稳定

- **风险等级**: ★★★☆☆

- **影响**: 中（AI 任务排队或失败）
- **风险分类**: 外部依赖风险

#### 表现

OpenAI / DeepSeek / SD API 等外部 AI 服务出现高延迟、频繁限流（429）、或服务中断。高峰期（如美国白天）API 响应时间可能从正常的 2 秒延长到 10 秒以上。

#### 缓解措施

   - 所有 AI 请求通过 Celery 队列管理
   - 限流时自动排队，按优先级处理
   - 失败时指数退避重试（1s → 2s → 4s → 8s → 16s，最大 32s）

   - 非紧急任务（如历史项目回溯分析）自动调度到低峰时段
